# Privacy-Preserving Threat Detection for Smart Home IoT Networks Using Federated Learning

A federated learning (FL) system that trains an intrusion/threat-detection model across
many simulated "smart homes" **without** raw traffic data ever leaving a device. Each
home trains locally on its own network traffic; only model updates (optionally
noised with differential privacy) are sent to a central aggregator.

## Why federated learning here?

Smart-home IoT traffic is sensitive (occupancy patterns, device habits, camera/mic
usage). A centralized IDS would require every household to upload raw traffic — a
privacy non-starter and a fat target for a data breach. Federated learning flips this:

- **Data stays local.** Each simulated home ("client") keeps its traffic on-device.
- **Only gradients/weights travel.** The server only ever sees model updates.
- **Differential privacy** adds calibrated noise to updates so no single home's
  traffic can be reverse-engineered from what it contributes.
- **Non-IID aware.** Real homes have different device mixes (cameras vs. thermostats
  vs. plugs), so this project explicitly simulates non-IID data across clients,
  which is the hard, realistic version of the FL problem.

## Dashboard

A role-based web dashboard (Flask, session auth, RBAC) that visualizes the
training curve and real model-generated alerts, with admin/analyst/viewer
roles that get progressively less identifiable data — the dashboard applies
the same privacy-by-design principle as the FL system itself. Full setup,
security notes, and default accounts are in
[`dashboard/README.md`](dashboard/README.md).

## The dataset

Real-world options you should swap in for serious work (all public, all require you
to download them yourself — see `data/prepare_data.py` for loader stubs):

- **N-BaIoT** — traffic from 9 real IoT devices infected with Mirai/BASHLITE.
- **TON_IoT** — telemetry + network + OS logs from a IoT/IIoT testbed (UNSW).
- **CICIoT2023** — 105 IoT devices, 33 attack types across 7 categories (DDoS,
  DoS, recon, web-based, brute force, spoofing, Mirai).

Because this environment has no internet access to those hosts, `prepare_data.py`
ships with a **synthetic traffic generator** that mimics the feature schema used by
these datasets (packet size stats, inter-arrival time stats, flow duration, protocol
one-hot, byte/packet rate) and injects labeled attack patterns (Mirai-style scan,
DDoS flood, brute force). This lets the full pipeline run end-to-end out of the box;
swap in real CSVs later with zero changes to `src/`.

## Quickstart

```bash
pip install -r requirements.txt

# 1. Generate/partition data across N simulated smart homes (non-IID)
python data/prepare_data.py --num_clients 10 --non_iid_alpha 0.3

# 2. Run the federated simulation (server + all clients in one process)
python src/server.py --rounds 20 --num_clients 10 --dp_noise_multiplier 1.0

# 3. (Optional) Run the non-federated baseline for comparison
python src/centralized_baseline.py
```

Global model checkpoints and a `metrics.csv` (per-round accuracy/F1/loss, both
federated and per-client) land in `models/`.

## Privacy mechanism (what's actually protecting the data)

1. **Local-only raw data.** Clients never serialize or transmit traffic samples,
   only model weight deltas.
2. **Gradient clipping + Gaussian noise (DP-SGD style)**, in `src/privacy.py`. Each
   client clips its update to a max L2 norm, then adds calibrated Gaussian noise
   before sending it to the server — bounding how much any single client's data can
   influence, or be inferred from, the aggregate.
3. **A (ε, δ) privacy budget accountant stub** using a simple moments-accountant
   approximation, so you can report an epsilon for your writeup. For production use,
   swap in Opacus's accountant (`pip install opacus`) — a hook is left in
   `src/privacy.py`.
4. **Secure aggregation (conceptual)**: the server strategy is structured so a real
   secure-aggregation protocol (e.g., pairwise-masking) could be dropped in at the
   `aggregate_fit` step — noted with a TODO in `src/server.py` — so the server itself
   never sees an individual client's raw update, only the sum.

## Threat model covered

- **Botnet recruitment scans** (Mirai-style TCP SYN scanning)
- **DDoS traffic floods** originating from a compromised device
- **Credential brute-forcing** against IoT admin interfaces
- **Benign** baseline traffic

This is a **multi-class classifier** (`benign`, `scan`, `ddos`, `brute_force`), not
just binary anomaly detection, so you can report per-attack precision/recall.

## Extending this into a real project

- Swap `prepare_data.py`'s synthetic generator for a real parser of N-BaIoT/TON_IoT/
  CICIoT2023 CSVs (schema notes are in that file).
- Replace the simulated multi-client loop in `server.py` with Flower's actual
  distributed deployment (`flwr.server.start_server` + real client processes/devices,
  e.g., one process per Raspberry Pi).
- Add TLS between clients and server (Flower supports this natively).
- Try FedProx or FedAdam strategies (`flwr.server.strategy`) instead of FedAvg for
  better convergence under non-IID data.
- Add a model-poisoning defense (e.g., Krum, trimmed mean) to `server.py`'s
  aggregation step, since FL is vulnerable to malicious clients.
